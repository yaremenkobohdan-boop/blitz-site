Workers у режимі "static assets". GitHub-репозиторій `yaremenkobohdan-boop/blitz-site`, гілка
`main`, є єдиним джерелом правди. Хмарна робоча копія: `/home/claude/blitz-site`.

## ⚠️ build.py — НЕ ЗАПУСКАТИ

У корені є `build.py`. **Він застарілий і не відображає жодного з ручних правок**, зроблених
у HTML напряму за останні сесії (модалка радіо, форма Uspacy, соцмережі в шапці, schema.org,
і т.д. — перевірено grep'ом, збігів нема). Якщо його запустити й перегенерувати сайт —
усі ці правки буде мовчки знищено. **Усі зміни вносяться напряму в `.html`-файли.**
Якщо колись знадобиться "переродити" build.py під поточний стан сайту — це окрема задача,
не роби цього мимохідь.

## Як пушити зміни (device-bridge workflow)

Ця хмарна сесія не має прямого доступу в інтернет для `git push` під обліковим записом
користувача. Пуш робиться через комп'ютер користувача (Mac), підключений через
remote-devices bridge. Послідовність (перевірена й робоча):

1. У хмарному контейнері: `git add` + `git commit` як завжди.
2. `git format-patch -1 HEAD --binary` → отримати `.patch`-файл.
3. `SendUserFile` на цей patch → отримати `file_uuid`.
4. `mcp__remote-devices__device_commit_files` — записати patch у підключену папку користувача
   (`/Users/gonki/Projects` на Mac).
5. `mcp__remote-devices__device_request_delete_permission` на цю ж папку — **потрібно
   запитувати практично щоразу заново** (дозвіл не зберігається між сесіями/перепідключеннями
   пристрою).
6. `mcp__remote-devices__device_bash` (це шел усередині VM, де підключені папки змонтовані як
   `$HOME/mnt/<назва-папки>`, тобто `$HOME/mnt/Projects` — **НЕ** сирий шлях хоста
   `/Users/gonki/Projects`, який використовують `device_list_dir`/`device_stage_files`/
   `device_commit_files`):
   ```bash
   cd $HOME/mnt/Projects
   git clone https://<GITHUB_PAT>@github.com/yaremenkobohdan-boop/blitz-site.git blitz-site-push
   cd blitz-site-push
   git config user.email "yaremenko.bohdan@gmail.com"
   git config user.name "Bohdan Yaremenko"
   git am /path/to/patch
   git push origin main
   cd .. && rm -rf blitz-site-push /path/to/patch
   ```
   Git-конфіг (`user.email`/`user.name`) треба виставляти **щоразу заново на свіжому клоні** —
   інакше `git am` падає з "Committer identity unknown".
7. У хмарному контейнері після пушу: `git fetch origin && git reset --hard origin/main`
   (обов'язково — і щоб підхопити контент, і бо `git am` на Mac-клоні створює інший хеш
   комміту, ніж оригінальний в контейнері).

**PAT для пушу**: НІКОЛИ не писати в цей файл і в репозиторій (GitHub secret scanning
блокує пуш комітів з реальним токеном у тексті — це вже траплялось). Постійного токена нема:
на початку кожної сесії правок попроси власника створити тимчасовий fine-grained PAT (scope —
лише репо `blitz-site`, Contents: read/write) і підстав його в URL клону замість
`<GITHUB_PAT>`. Після сесії нагадай власнику **відкликати** цей токен. Токен, який
використовувався в сесіях до 06.10.2026, треба вважати скомпрометованим (він світився в
історії чатів) — відкликати.

**Deploy hook Cloudflare** (URL зберігається в пам'яті Claude Project, не тут): після пушу
власник сам викликає його через `curl -X POST <hook>` у Терміналі — автовебхук GitHub →
Cloudflare ненадійний. Завжди нагадуй про це в кінці кожного пушу.

**Контрольний список після кожної зміни**: пуш успішний → `git fetch && git reset --hard
origin/main` у хмарі → прибрати клон і patch на Маку → нагадати про deploy hook.

**Після кожного пушу власник сам тригерить Cloudflare deploy hook**, щоб зміни стали живими —
пуш у GitHub сам по собі сайт не оновлює.

## Браузерна автоматизація

- `mcp__remote-devices__Control_Chrome__*` (локальний MCP-сервер "Control Chrome" на Маку) —
  **ненадійний для читання контенту** в цій обстановці: `list_tabs`/`open_url` працюють, але
  `get_page_content`/`execute_javascript` стабільно падають з "Google Chrome is not running"
  навіть одразу після успішного `open_url`. Схоже, список вкладок береться зі
  stale/cached session-restore даних, а не з живого CDP-з'єднання. **Не використовувати.**
- `mcp__claude-in-chrome__*` (розширення Chrome) — працює надійно, підхоплює залогінені сесії
  користувача (Google, Facebook і т.д.) в тому ж реальному профілі Chrome. Створює вкладки у
  своїй окремій групі вкладок. Завантажувати інструменти одним викликом ToolSearch:
  `select:mcp__claude-in-chrome__tabs_context_mcp,...navigate,...computer,...read_page,...tabs_create_mcp,...tabs_close_mcp`.
  Закривати вкладки через `tabs_close_mcp` після використання.
- **Вбудована панель Google "Ваша компанія в Google" (business.google.com, і те саме через
  Google Maps → "Керувати профілем компанії") — крихка й ненадійна для автоматизованих правок.**
  Двічі (у двох різних сесіях) спроби змінити категорію бізнесу й адресу провалились: кнопка
  "Підтвердити" нічого видимо не робила, або модалка не рендерилась попри зміну URL-хеша, або
  скрол усередині модалки зависав. Обидва рази перевірено (свіжим read-only заходом), що
  профіль лишився в початковому стані — жодних побитих/часткових змін не залишилось.
  **Висновок: не намагатись автоматизувати правки в цій конкретній поверхні Google UI.**
  Давати власнику точні мануальні кроки замість цього.

## Наступна задача: піддомени (ще не розпочата)

Власник планує додавати піддомени `*.blitz.com.ua`. **Рішення по архітектурі ще не
прийнято** — спочатку з'ясуй у нього, які саме піддомени й для чого. Відомі варіанти
(зафіксовані раніше щодо піддоменів радіостанцій):
- **А** — розділ/сторінки на тому ж сайті (один Worker, піддомен лише як alias/redirect);
- **Б** — окремий Cloudflare Worker (і окрема директорія/репо) під кожен піддомен, Custom
  Domain на кожен Worker, спільні ассети (лого, style.css) або дублюються, або беруться з
  основного домену.
Питання, які треба поставити власнику ДО будь-яких змін: (1) повний список піддоменів і що
на кожному має бути (міста? послуги? радіостанції?); (2) чи піддомен — окремий сайт зі
своїм контентом, чи дзеркало/редирект; (3) чи потрібні окремі форми Uspacy на кожному.
Технічні чек-пункти для кожного піддомена: Worker + Custom Domain у Cloudflare
(DNS-запис додається автоматично при прив'язці Custom Domain; ручні записи не ламати),
`robots.txt` + `sitemap.xml` + `llms.txt` окремо на піддомен, `<link rel="canonical">`,
schema.org (`url`, `sameAs`), перелінковка з головного сайту (меню/футер), оновити
`sitemap.xml` головного домену і CLAUDE.md. Піддомени, що вже існують і НЕ є частиною цього
сайту: `crm.blitz.com.ua` (CRM). Окремий проєкт `blits-fm.ua` — інший сайт, не плутати.
